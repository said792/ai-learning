# دليل الرفع المباشر إلى Supabase Storage

## 1) المشكلة التي تم حلها

عند رفع ملف كبير كان التطبيق يرسل الملف كاملًا عبر Vercel:

```
المتصفح ← Vercel API ← Supabase Storage
```

Vercel يرفض أي جسم طلب أكبر من **4.5 MB** على Serverless Functions، فيرجع الخطأ:

```
HTTP 413 Payload Too Large
```

## 2) الحل: الرفع المباشر من المتصفح

الملف لم يعد يمر على Vercel أثناء الرفع إطلاقًا:

```
1) المتصفح ← Vercel  :  طلب JSON خفيف (init) — اسم وحجم الملف فقط
2) المتصفح ← Supabase :  رفع الملف نفسه مباشرة (Signed URL أو TUS)
3) المتصفح ← Vercel  :  طلب JSON خفيف (complete) — تسجيل وتحليل Gemini
```

كل طلب يمر على Vercel أصبح بلا محتوى ملف، فيختفي خطأ 413 نهائيًا.

## 3) طريقتا الرفع (الخادم يختار تلقائيًا)

| الطريقة | متى؟ | المزايا |
| --- | --- | --- |
| `direct` | الملف ≤ 25MB (قابل للتعديل) | POST واحد للـ Signed Upload URL مع شريط تقدم |
| `resumable` (TUS) | الملف أكبر من 25MB | رفع مقسّم 6MB، **استكمال تلقائي عند انقطاع الإنترنت**، استكمال بعد إعادة تحميل الصفحة، إلغاء |

- لا يوجد أي حد حجم مفرض من كود التطبيق — الأكبر فقط يستخدم TUS، ولا يُرفض أي حجم.
- حد TUS لدى Supabase: جلسة الرفع صالحة 24 ساعة، والـ Signed URL صالح ساعتين.
- لو فشل إنشاء جلسة TUS لأي سبب (إصدار أقدم من Storage مثلًا) تتحول الواجهة تلقائيًا للرفع المباشر بطلب واحد كخطة بديلة، ولو مسارات الرفع المباشر غير منشورة بعد ترجع للرفع القديم عبر Vercel.

## 4) الحفاظ على كل الوظائف كما هي

الفحص النهائي والتسجيل يحدثان في خطوة `complete` بنفس منطق المسار القديم بالترتيب نفسه (منقول حرفيًا إلى `lib/documents/process.ts` المشترك):

- فحص الامتدادات المدعومة قبل بدء الرفع (في `init` أيضًا).
- حدود الباقات اليومية والشهرية + حد الزوار (3 ملفات يوميًا) — فحص مبدئي في `init` وفحص نهائي + تسجيل الاستخدام في `complete`.
- منع تكرار الملفات بالهاش SHA-256 — يظل يعمل بالكامل لأن الهاش يُحسب من الملف بعد تنزيله على الخادم، ولو كان الملف محلاًلًا مسبقًا يُرجع التحليل المحفوظ بدون خصم استخدام.
- تسجيل الملف في قاعدة البيانات بنفس الحقول والحالات (processing → completed / failed).
- التحليل بـ Gemini بالعربية أو الإنجليزية + إعادة التحليل بلغة أخرى للملف الموجود.
- استخراج النص للصور والصوت والفيديو (ffmpeg + Gemini) كما هو تمامًا.
- صور المستندات (document_assets) واقتراح التصنيف كما هما.
- كوكي الزائر `ai_guest_id` يُنشأ في `init` ويُستخدم في `complete`.

## 5) الأمان (بدون أي تغيير في نموذج حماية المشروع)

المشروع يمنع أي وصول مباشر من المتصفح بـ RLS بدون سياسات عامة، ولم نكسر ذلك:

1. **Signed Upload URL** — يُبنى على الخادم بمفتاح `service role`، صالح ساعتين، ومرتبط بمسار واحد محدد عشوائي (`pending/<uuid>.<ext>`) لا يمكن تخمينه.
2. **توكين جلسة HMAC-SHA256** — يصدره الخادم في `init` ويشترطه `complete`، ويربط الجلسة بهوية المستخدم/الزائر + المسار + اللغة + التصنيف + مدة الصلاحية. أي تلاعب بالمسار أو المحاولة باسم مستخدم آخر تُرفض (اختبرناها: تزييف التوقيع، تزييف الحمولة، الانتهاء، عدم مطابقة الهوية — كلها مرفوضة).
3. لا يظهر في المتصفح إلا `NEXT_PUBLIC_SUPABASE_URL` (عام أصلًا) والتوكن الموقّع المؤقت.
4. رفع TUS من المتصفح يستخدم هيدر `x-signature` بالتوكن الموقّع — بلا أي مفتاح خدمة، وبلا أي تغيير في سياسات RLS.
5. الملف يُرفع أولًا لمجلد `pending/` ولا ينتقل لمساره النهائي `<hash>/<uuid>.<ext>` إلا بعد التحقق والفحوص، ويُحذف تلقائيًا لو تكرر أو وُصل لحد الباقة.
6. تنظيف تلقائي احتمالي (5% من طلبات init) للملفات المهملة في `pending/` الأقدم من 24 ساعة.

## 6) الملفات التي تغيرت

### ملفات جديدة
| الملف | الوظيفة |
| --- | --- |
| `lib/documents/shared.ts` | دوال الهوية والباقات والاستخدام المشتركة (منقولة كما هي من المسار القديم) |
| `lib/documents/upload-config.ts` | إعدادات خط الرفع القابلة للتعديل من متغيرات البيئة |
| `lib/documents/upload-session.ts` | توكين جلسة الرفع HMAC (إنشاء + تحقق + مطابقة هوية) |
| `lib/documents/process.ts` | خط المعالجة الموحد: hash → منع تكرار → باقة → تخزين → استخراج → تحليل |
| `app/api/documents/upload/init/route.ts` | الخطوة 1: تحقق + حدود الباقة + Signed URL + توكين الجلسة |
| `app/api/documents/upload/complete/route.ts` | الخطوة 3: تنزيل من التخزين + التسجيل + التحليل |
| `lib/upload/browser-upload.ts` | وحدة الرفع في المتصفح: XHR بالتقدم + عميل TUS مصغر مع استكمال |

### ملفات معدلة
| الملف | التغيير |
| --- | --- |
| `app/api/documents/upload/route.ts` | أُعيد هيكلته لاستخدام الخط الموحد — **نفس السلوك الخارجي**، ويظل كاحتياطي |
| `app/page.tsx` | دالة `uploadFile` تستخدم الرفع المباشر + شريط تقدم + زر إلغاء + رسائل استكمال |

لا يوجد أي تعديل على قاعدة البيانات أو ملفات SQL — لا حاجة لتشغيل أي migration.
لا توجد حزم جديدة — لا حاجة لـ `tus-js-client` (العميل مكتوب داخليًا بمكتبة fetch/XHR فقط).

## 7) متغيرات البيئة

لا يوجد متغير جديد **مطلوب**. الموجود يكفي:

- `NEXT_PUBLIC_SUPABASE_URL`
- `SUPABASE_SERVICE_ROLE_KEY`

اختيارية للضبط الدقيق (كلها لها قيم افتراضية):

| المتغير | الافتراضي | الوظيفة |
| --- | --- | --- |
| `UPLOAD_DIRECT_MAX_MB` | `25` | حد التحويل للرفع المقسّم (الملفات الأكبر ترفع TUS تلقائيًا) |
| `UPLOAD_SESSION_SECRET` | مشتق من مفتاح الخدمة | مفتاح مستقل لتوقيع جلسات الرفع (مفيد لو تدوير مفتاح الخدمة) |

## 8) حدود حجم الملف الفعلية (خارج كود التطبيق)

إلغاء حد التطبيق لا يلغي حدود المزود:

| المصدر | الحد |
| --- | --- |
| Supabase Free | حتى **50 MB** للملف (من Dashboard → Storage → Settings → Global file size limit) |
| Supabase Pro | قابل للرفع حتى **500 GB** للملف من نفس الإعداد |
| مساحة التخزين | Free: 1GB — Pro: 100GB ثم مدفوع بالاستخدام |
| رسالة الخطأ | لو تجاوز المستخدم حد الخطة تظهر رسالة عربية واضحة داخل التطبيق |

عند الترقية إلى **Pro** لا تحتاج تعديل أي كود — فقط ارفع القيمة من إعدادات التخزين في Dashboard؛ الملفات الكبيرة ستستخدم TUS تلقائيًا لأنها أكبر من 25MB.

## 9) حدود عملية للمعالجة بعد الرفع (تنبيه صادق)

- رفع ملف 100MB+ يعمل، لكن خطوة `complete` تنزّل الملف على Function للمعالجة (ffmpeg / استخراج نص / تحليل) — ملفات **متعددة الجيجابايت** قد تُرفع للتخزين بنجاح لكن معالجتها محدودة بذاكرة Function ومساحة `/tmp`.
- نسخ الصوت/الفيديو تمر على Gemini (Files API) ولها حدود مدة/حجم خاصة بها.
- هذه حدود مزودين، وليست حدودًا مضافة من كود التطبيق.

## 10) خطوات النشر

1. ارفع الملفات المعدلة إلى المستودع وانشر على Vercel (لا migrations، لا حزم جديدة).
2. جرّب ملفًا صغيرًا (< 25MB) — يجب أن يظهر "جاري رفع الملف مباشرة..." مع نسبة تقدم.
3. جرّب ملفًا كبيرًا (> 25MB) — يجب اختيار TUS تلقائيًا، وجرّب إعادة تحميل الصفحة أثناء الرفع ثم اضغط "رفع وتحليل" على نفس الملف — يستكمل من حيث توقف.
4. راقب سجلات Vercel: `[UploadInit]` و `[UploadComplete]` و `[Documents]` كما في السابق.
5. لو أردت تغيير حد التحويل: أضف `UPLOAD_DIRECT_MAX_MB` في إعدادات Vercel.

## 11) ملاحظات للفريق

- المسار القديم `POST /api/documents/upload` يعمل كما هو — ممكن استخدامه مؤقتًا أو تعطيله لاحقًا بثقة بعد التحقق.
- رسالة المستخدم عند فشل الشبكة أثناء رفع كبير تشجعه على إعادة المحاولة لأن الاستكمال تلقائي.
- ملفات `pending/` الفاشلة تُحذف تلقائيًا خلال 24 ساعة ولا تظهر في المكتبة أبدًا.
